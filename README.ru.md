Лёгкий Telegram-уведомитель о **новых устройствах в сети на роутере OpenWrt**, включая основную **и гостевую** сеть. Один скрипт на POSIX sh: без сканирования, без базы данных, без демонов и веб-интерфейса.

## Возможности

- 🆕 Уведомление, когда новый MAC-адрес получил DHCP-адрес
- 🔄 Уведомление о смене IP у известного устройства (можно отключить)
- 🔙 Уведомление, когда устройство вернулось после отсутствия дольше N дней (порог настраивается, можно отключить)
- Отдельные названия основной и гостевой сетей
- Несколько получателей в Telegram; один бот может обслуживать несколько роутеров (в конце сообщения стоит пометка роутера)
- Очередь повторной отправки: если Telegram или интернет недоступны, сообщения сохраняются и уходят позже
- Необязательное определение производителя, пометка случайных (приватных) MAC
- Очень низкая нагрузка: чтение небольшого файла раз в минуту; во flash пишется только при изменениях

## Как это работает

Раз в минуту cron запускает `lanwatch-leases`. Скрипт читает `/tmp/dhcp.leases` (файл аренд, который dnsmasq и так ведёт), сравнивает его с небольшой локальной базой `/etc/lanwatch/devices.db` и отправляет сообщение в Telegram, если произошло что-то заслуживающее внимания. Сеть не сканируется.

> Почему cron, а не хук `dhcpscript` в dnsmasq? В OpenWrt 24.10 dnsmasq работает в изолированной среде, и хук не может прочитать собственный конфиг. Чтение файла аренд из cron обходит эту проблему и не меняет настройки dnsmasq.

Пример сообщения:

```
🆕 Новое устройство в сети

Имя: iPhone
IP: 192.168.50.23
MAC: 3c:a0:67:57:0d:bb
Производитель: Samsung Electro-Mechanics
Сеть: Гостевая сеть

🛜 Router 1
```

## Требования

- OpenWrt 24.10 (проверено). OpenWrt 25.x (менеджер пакетов `apk`) должен работать, но я не проверял
- dnsmasq в роли DHCP-сервера (по умолчанию)
- Пакеты `curl` и `ca-bundle`
- Токен Telegram-бота и ваш chat id (или несколько)

## Настройка

Все параметры находятся в `/etc/lanwatch/config` (см. [src/config.example](src/config.example)).

| Параметр | Назначение |
|---|---|
| `BOT_TOKEN` | Токен бота от @BotFather |
| `CHAT_IDS` | Получатели через пробел (у групп chat id обычно отрицательный) |
| `ROUTER_NAME` | Пометка в конце каждого сообщения (пусто = без пометки) |
| `MAIN_IF`, `GUEST_IF` | Интерфейсы, на которых работает DHCP, например `br-lan`, `br-guest` |
| `VENDOR_LOOKUP` | `1` = определять производителя через api.macvendors.com (отправляются только первые 3 байта MAC), `0` = выключено |
| `EVENT_IP` | `1` = уведомлять о смене IP, `0` = выключено |
| `RETURN_DAYS` | Уведомлять о возвращении устройства после отсутствия дольше N дней, `0` = выключено |
| `MAX_PER_HOUR` | Максимум уведомлений в час, 0 = без ограничения (при превышении приходит одно предупреждение) |

## Плюсы и минусы по сравнению с полноценными сканерами сети

Полноценные сканеры решают более широкую задачу. Этот проект решает узкую: *сообщить, когда в сети появилось что-то новое*.

**Плюсы**

- Работает на самом роутере: не нужен отдельный сервер, Docker или веб-сервис
- Видит гостевую сеть, потому что читает собственные DHCP-аренды роутера (не нужно настраивать VLAN и firewall для сканера)
- Всегда показывает актуальный IP устройства: изменения отслеживаются по MAC
- Нет активного сканирования: нет лишнего трафика и проб портов
- Крошечный: один shell-скрипт и `curl`; нагрузка на CPU и память пренебрежимо мала
- Уведомления переживают сбои (очередь повторной отправки), несколько получателей, несколько роутеров на одном боте

**Минусы**

- Видны только устройства, использующие DHCP; устройство со статическим IP остаётся незаметным
- Нет веб-интерфейса, графиков, истории и статуса «онлайн / офлайн»
- Нет сканирования портов, определения ОС и сервисов
- Задержка до минуты (интервал cron)
- Телефоны с приватными (случайными) MAC могут выглядеть как новые устройства
- Зависит от файла аренд dnsmasq; другие DHCP-серверы не поддерживаются
- Имена устройств сокращаются до латиницы, цифр и символов `. _ ( ) -`

## Безопасность

- Токен бота хранится открытым текстом в `/etc/lanwatch/config` (права `600`, читает только root). Не публикуйте его
- Токен входит в URL запроса, поэтому на роутере он может кратко быть виден в списке процессов
- При `VENDOR_LOOKUP='1'` первые три байта MAC-адреса *новых* устройств отправляются на api.macvendors.com
